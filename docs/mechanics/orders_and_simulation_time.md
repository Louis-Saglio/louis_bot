# Orders and simulation time

How player/AI commands travel from issue to effect, and how the simulation clock works, in 0 A.D. 0.28.0. Grounded in `source/source/simulation2/system/TurnManager.{h,cpp}`, `source/source/simulation2/system/LocalTurnManager.cpp`, `source/source/simulation2/Simulation2.cpp`, `source/source/simulation2/components/CCmpCommandQueue.cpp`, `source/source/simulation2/components/CCmpAIManager.cpp`, `source/source/ps/Game.cpp`, `public/simulation/helpers/Commands.js`, `public/simulation/components/UnitAI.js` and `public/simulation/components/Timer.js` (all paths relative to `/home/ubuntu/0ad-reference`).

## The fixed-timestep turn model

The simulation advances in **turns** of a fixed length:

- **Default turn length: 200 ms** (simulation time), `DEFAULT_TURN_LENGTH = 200` (`source/source/simulation2/system/TurnManager.h:62`). Same value in single-player and multiplayer; a single-player game uses `CLocalTurnManager` with this default (`source/source/simulation2/system/LocalTurnManager.cpp:30-33`).
- One rendered frame does **not** equal one turn. Each frame, the engine adds the elapsed (scaled) frame time to an accumulator `m_DeltaSimTime` and runs one turn per full 200 ms accumulated (`source/source/simulation2/system/TurnManager.cpp:74-164`). The accumulator is clamped to 2 turn lengths (400 ms), so a laggy machine fast-forwards at most 2 turns per frame (`TurnManager.cpp:81-84`).
- Inside a turn, `CSimulation2Impl::Update` converts the turn length to a fixed-point `0.2` second `turnLengthFixed` and runs the update phases in order (`source/source/simulation2/Simulation2.cpp:369-409`, `519-596`):
  1. pathfinder: send requested paths;
  2. broadcast `TurnStart`;
  3. **`CommandQueue.FlushTurn(commands)` — all commands scheduled for this turn are executed** (`CCmpCommandQueue.cpp:116-138`);
  4. pathfinder: process move commands generated by step 3;
  5. broadcast `Update` (most components, incl. `Timer` and production);
  6. broadcast `Update_MotionFormation`, then process formation move commands;
  7. broadcast `Update_MotionUnit` (unit movement);
  8. broadcast `Update_Final`;
  9. flush destroyed entities; then run the AI computation and push its commands (`Simulation2.cpp:578-586`).

Everything inside a turn sees the same `turnLength` (0.2 s). Movement, attacks, gathering, etc. are all integrated with this 200 ms step.

## When commands take effect

- Commands are not executed when issued; they are **scheduled for a future turn** in the turn manager's queue `m_QueuedCommands` (`TurnManager.h:203-204`, `AddCommand` at `TurnManager.cpp:218-241`). A command for a turn ≤ current turn is rejected (`TurnManager.cpp:222-231`).
- **Single-player command delay: 1 turn** (`COMMAND_DELAY_SP = 1`, `TurnManager.h:64-67`). A human/GUI command posted during turn N is scheduled for turn N+1 (`LocalTurnManager.cpp:35-43`). Multiplayer uses 4 turns (`COMMAND_DELAY_MP = 4`, `TurnManager.h:81`) — irrelevant to the harness, which runs single-process local games.
- **AI commands (the bot's path):** the AI runs in a separate script context. Its `Engine.PostCommand(playerid, cmd)` only buffers the command in the AI worker (`CCmpAIManager.cpp:318-331`). At the **end of each turn's update** the AI's shared `onUpdate` is called with a serialized game state (`Simulation2.cpp:580-586`, `CCmpAIManager.cpp:795-829`), the buffered commands are collected and pushed into the command queue's local list (`CCmpAIManager.cpp:1040-1061` → `CCmpCommandQueue.PushLocalCommand`, `CCmpCommandQueue.cpp:95-99`), and at the **start of the next turn** `FlushTurn` runs them through the JS global `ProcessCommand(player, cmd)` — local (AI) commands first, then network/turn-manager commands (`CCmpCommandQueue.cpp:116-138`).

So for a bot: **commands posted while processing the state of turn N are executed at the start of turn N+1, before that turn's movement/update phases.** Effective latency is exactly 1 turn = 200 ms of simulation time, plus the fact that the state the bot sees is already 1 turn old when its commands land.

### Command batching per turn

- There is no per-turn command limit. All commands buffered during a turn are executed, in order: AI/local commands first (in the order they were posted), then turn-manager commands grouped by client session ID for determinism (`TurnManager.h:53-56`, `TurnManager.cpp:143-149`).
- Two commands issued in the same turn to the same unit both execute in the same turn, sequentially. The second one can overwrite the first's effect (e.g. two non-queued `walk` commands: the second replaces the first's order before any movement happened).

## Command processing (`public/simulation/helpers/Commands.js`)

`ProcessCommand(player, cmd)` (`Commands.js:884-936`) is the single entry point for every command, human or AI:

1. `cmd.entities` is filtered to entities the player actually controls (`FilterEntityList`, `Commands.js:895-896`, `1824-1827`) — orders on enemy/gaia units are silently dropped.
2. A `playercommand` GUI notification is pushed (harmless for a bot).
3. The handler `g_Commands[cmd.type]` is invoked; an unknown `cmd.type` logs an error and does nothing (`Commands.js:928-935`). Most validity checks are **not** done here — the comment at `Commands.js:921-925` states target validity is UnitAI's job when the order executes, so invalid orders typically fail silently.

Relevant `cmd.type` values (with the UnitAI method each calls): `walk` → `Walk(x, z, queued, pushFront)` (`Commands.js:105-120`; multi-unit walks are distributed around the target point by the pathfinder); `walk-to-range` → `WalkToPointRange` (AI-only, `Commands.js:130-139`); `attack-walk` → `WalkAndFight` (`Commands.js:141-156`); `attack` → `Attack(target, allowCapture, queued, pushFront)` (`Commands.js:166-171`); `gather` → `Gather` (`Commands.js:211-219`); `gather-near-position` → `GatherNearPosition` (`Commands.js:221-226`); `returnresource` → `ReturnResource` (`Commands.js:228-236`); `repair` → `Repair` (also used to build foundations, `Commands.js:200-209`); `construct` → `TryConstructBuilding` (places a foundation, subtracts resources immediately, then auto-issues a `repair` order to the builders when `autorepair`, `Commands.js:359-362`, `1101-1281`); `train` / `research` / `stop-production` → production queue (`Commands.js:278-357`); `stop` → `Stop` (`Commands.js:484-489`); `stance` → `SwitchToStance` (`Commands.js:636-644`); `garrison`, `guard`, `patrol`, `heal`, `formation`, `barter`, `set-rallypoint`, `delete-entities`, etc. (full table in `g_Commands`, `Commands.js:5-882`).

Note: movement-type commands on several units go through `GetFormationUnitAIs` (`Commands.js:1541`), which may wrap the units in a formation entity and order the formation instead — for `cmd.formation == NULL_FORMATION` or queued orders formations are not forced (`Commands.js:898-902`).

## UnitAI order queue semantics (`public/simulation/components/UnitAI.js`)

Every unit has an **order queue**; the current order is always `orderQueue[0]` (also cached as `this.order`) (`UnitAI.js:3478-3479`). An order is `{ "type": ..., "data": ... }`; orders created from player/AI commands carry `data.force = true` (e.g. `Walk`, `UnitAI.js:5455-5461`), orders the unit creates on its own (auto-attack, flee, find-new-resource) carry `force = false` (e.g. `UnitAI.js:6088-6092`).

Three insertion modes, dispatched by `AddOrder(type, data, queued, pushFront)` (`UnitAI.js:5339-5350`):

- **`queued=false, pushFront=false` → `ReplaceOrder`** (`UnitAI.js:4106-4161`): clears the whole queue and makes the new order current. This is the default when a command's `queued` flag is absent/false — **issuing a command without `queued: true` wipes the unit's pending orders.**
- **`queued=true` → `PushOrder`** (`UnitAI.js:3968-3992`): appends to the back of the queue; executes immediately only if the queue was empty.
- **`pushFront=true` → `PushOrderFront`** (`UnitAI.js:3998-4025`): inserts at the front and executes immediately (used e.g. by `LeaveFoundation` and by the `call-to-arms` handler).

When the current order completes (or fails), `FinishOrder()` shifts the queue and starts the next order; with an empty queue the unit goes to `IDLE` (`UnitAI.js:3911-3962`). Formation members and packing/unpacking siege get special handling in `ReplaceOrder` (packing orders are preserved, `UnitAI.js:4117-4139`).

Common order types (the `Order.*` message the FSM receives): `Walk`, `WalkToTarget`, `WalkAndFight`, `Attack`, `Gather`, `ReturnResource`, `Repair`, `Heal`, `Garrison`, `Guard`, `Patrol`, `Stop`, `Cheer`, `Pack`/`Unpack`, `LeaveFoundation`, `Trade`, `CollectTreasure`. `WalkAndFight` lets units engage enemies matching `targetClasses` on the way; a plain `Walk` ignores enemies entirely. `Attack` on a unit that cannot attack the target degrades to `WalkToTarget` (`UnitAI.js:5555-5566`); `Gather` on an ungatherable target degrades to `WalkToTarget` too (`UnitAI.js:5646-5652`).

### Stances

Present in 0.28.0. Set per unit by the `stance` command (`SwitchToStance`, `UnitAI.js:5968-5980`, which also resets the held position and range queries); the stance name is read from `UnitAI.js:6175-6190`. Defined in `g_Stances` (`UnitAI.js:80-170`), each stance is a set of booleans controlling automatic behaviour:

| stance | attacks visible enemies | always retaliates | flees | chases | chases beyond vision | selectable |
|---|---|---|---|---|---|---|
| `violent` | yes | yes | no | yes | yes | yes |
| `aggressive` | yes | no | no | yes | no | yes |
| `defensive` | yes | no | no | no (holds ground) | no | yes |
| `passive` | no | no | yes | no | no | yes |
| `standground` | yes | no | no | no (never moves) | no | yes |
| `skittish` | no | no | yes (even on sight) | no | no | no |
| `passive-defensive` | no | no | no | no (holds ground) | no | no |
| `none` | no | no | no | no | no | no |

(`selectable: false` stances are not offered in the GUI but a bot can set them by command; `none` is documented as "only to be used by AI or trigger scripts", `UnitAI.js:158-159`.) The template's `DefaultStance` is applied at init (`UnitAI.js:3492`; schema at `UnitAI.js:6-16`). Edge case: with `violent`, `targetAttackersAlways` can override even forced (player-issued) orders (`UnitAI.js:66-69`, `1542-1543`).

### Main states (overview)

UnitAI is a finite state machine (`helpers/FSM.js`), initialised to `INDIVIDUAL.IDLE` (or `FORMATIONCONTROLLER.IDLE` for formation controllers) (`UnitAI.js:3647-3652`). Top-level branches: `FORMATIONCONTROLLER` (moves/attacks as a group, delegates to members), `FORMATIONMEMBER` (follow formation offsets), and `INDIVIDUAL` — the normal case. Under `INDIVIDUAL` (`UnitAI.js:1540` on): `IDLE` (animals roam via timers), `WALKING`, `WALKINGANDFIGHTING`, `PATROL`, `GUARD`, `FLEEING`, `COMBAT` (sub-states `APPROACHING`/`ATTACKING`/`FINDINGNEWTARGET`/`CHASING`), `GATHER` (`APPROACHING`/`GATHERING`/`RETURNINGRESOURCE`...), `HEAL`, `RETURNRESOURCE`, `COLLECTTREASURE`, `TRADE`, `REPAIR`, `GARRISON`, `CHEERING`, `PACKING`/`UNPACKING`, `PICKUP`. Transitions are message-driven (`Order.<Type>` when an order starts, `MovementUpdate` from UnitMotion, `Timer`, `LosRangeUpdate` from range queries, `Attacked`...), not polled per turn.

## Timers and the simulation clock (`public/simulation/components/Timer.js`)

- `Timer` is a system component. `GetTime()` returns **elapsed simulation time in milliseconds**; it advances by exactly the turn length each turn: `OnUpdate` receives `turnLength` in seconds, converts with `Math.round(msg.turnLength * 1000)` and adds it (`Timer.js:108-112`). Simulation time therefore advances in discrete 200 ms steps, independent of wall-clock.
- `SetTimeout(ent, iid, funcname, time, data)` / `SetInterval(..., repeattime)` schedule a component method call after at least `time` ms (`Timer.js:41-73`). Timers are only checked once per turn, so **any timer fires at the first turn boundary at or after its due time** — a 100 ms timer fires 200 ms later (1 turn), and the callback receives the overshoot as `lateness` in ms (`Timer.js:30-39`, `116-164`). Repeating timers re-fire within the same turn if still due.
- Timers on destroyed entities are silently dropped (`Timer.js:130-136`).
- `GetLatestTurnLength()` exposes the current turn length in ms (`Timer.js:25-28`).
- All template durations (build times, attack prepare/repeat, gather rates) are ultimately consumed through these timers or per-turn updates, so they tick in simulation time: at game speed 1×, 200 sim-ms elapse per 200 wall-clock-ms; at other speeds the sim clock decouples from wall-clock.

## Game speed: wall-clock vs simulation time

- Game speed is a multiplier `m_SimRate` (default 1.0) on the real frame time before it feeds the turn accumulator: `deltaSimTime = deltaRealTime * m_SimRate` (`source/source/ps/Game.cpp:419-449`). It is set from the `gameSpeed` init attribute (`Game.cpp:244-251`), itself settable with `-autostart-speed` (`public/autostart/cmd_line_args.js:168-169`).
- The GUI offers speeds 0.1× to 20× (`public/simulation/data/settings/game_speeds.json`, default `Normal (1×)`).
- **The turn length never changes: it is always 200 ms of simulation time.** Speed only changes how much wall-clock time buys one turn: at 0.5× a turn takes 400 ms wall-clock, at 2× 100 ms. Commands, timers, build times, speeds are all expressed in simulation time and are unaffected.
- Per frame at most `maxTurns = (size_t)m_SimRate` turns run, always at least 1 (`Game.cpp:428-434`, `TurnManager.cpp:108`), so at speed ≤ 1× the sim advances at most one turn per rendered frame; catch-up after lag is capped at 2 turns per frame (`TurnManager.cpp:81-84`).
- **Headless mode (`-autostart-nonvisual`, what the harness uses) ignores the frame-rate pacing entirely:** `NonVisualFrame` calls `TurnManager::Update(DEFAULT_TURN_LENGTH, 1)` directly, so exactly **one turn per engine frame, as fast as the CPU can compute it**, regardless of game speed (`source/source/main.cpp:493-512`). A 20-game-minute match is 6000 turns.

## Edge cases a bot should care about

- **1-turn latency everywhere:** state seen at turn N, commands land at turn N+1 start, effects visible at turn N+1 end at the earliest.
- **Same-turn overwrite:** two non-queued commands to the same unit in one turn → the second silently replaces the first.
- **`ReplaceOrder` wipes the queue:** to build order chains (walk then gather then return), every command after the first must carry `queued: true`.
- **Silent failures:** `ProcessCommand` filters uncontrollable entities and most handlers don't validate targets (`Commands.js:921-925`); an order on a dead/invalid target is dropped or degrades (e.g. `Attack` → `WalkToTarget`) without an error the bot can see.
- **Timer granularity:** nothing in the simulation happens between turns; sub-200 ms timings quantize to turn boundaries.
- **Stance interference:** `violent` stance can hijack units mid-order (`targetAttackersAlways` overrides forced orders); a bot that wants deterministic control should consider `standground`/`passive` or the AI-only `none` stance.
